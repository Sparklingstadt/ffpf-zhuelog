# 認証

API の利用者は 3 種類です。ログインに成功すると、どちらも同じ形のトークンの組（アクセストークンとリフレッシュトークン）を受け取ります。

| 役割（`role`） | ログイン方法                       | `ownerId`（ノートの所有者 ID）          |
| -------------- | ---------------------------------- | --------------------------------------- |
| `admin`        | GitHub（PKCE）。許可リストに載る人 | GitHub の数値 ID（例：`12345678`）      |
| `member`       | ログイン ID とパスワード           | `password:` + `PasswordAccount` の `id` |
| `guest`        | `POST /v1/auth/guest`（認証なし）  | `guest`（固定）                         |

`ownerId` は Web と同じ値で、ノートやフォローの所有者を表します。ゲストはデータを持たず、使えるのは `GET /v1/me` だけです。

## GitHub ログイン（admin）

```text
アプリ ──(1) 認可画面を開く（PKCE S256）──▶ GitHub
アプリ ◀─(2) カスタム URL スキームで code ── GitHub
アプリ ──(3) POST /v1/auth/github {code, codeVerifier, redirectUri}──▶ API
API    ──(4) code + code_verifier + client_secret を交換、GET /user──▶ GitHub
アプリ ◀─(5) {accessToken, refreshToken, expiresIn} ── API
```

1. アプリは PKCE（S256）で GitHub の認可画面を開き、モバイル用 OAuth App のカスタム URL スキームで `code` を受け取ります。
2. `POST /v1/auth/github` に `{code, codeVerifier, redirectUri}` を送ります。`redirectUri` は API の `GITHUB_MOBILE_REDIRECT_URI` か、設定してあれば `GITHUB_WEB_REDIRECT_URI` と完全に一致していなければなりません。一致した方の OAuth App（モバイル用か Web 用）で `code` を交換します。
3. API は `client_secret` と `code_verifier` を付けて GitHub のトークンエンドポイントで `code` を交換し、`GET /user` で数値 ID とログイン名を得ます。GitHub への通信はそれぞれ 10 秒でタイムアウトします。GitHub のアクセストークンは保存しません。
4. GitHub の **数値のユーザー ID** を許可リスト（`AUTH_ALLOWED_GITHUB_IDS`）と照合します。含まれなければ `403 forbidden` です。ログイン名は本人が変えられ、手放された名前は他人が取得できるので、許可の判定には使いません（トークンに情報として残るだけです）。
5. `ownerId` を GitHub の数値 ID、`role` を `admin` としてトークンを発行します。

`code`・`codeVerifier`・`redirectUri` を GitHub が拒否したとき（`bad_verification_code` など）や `redirectUri` が一致しないときは `401 unauthorized`、GitHub に届かない・応答が不正なときは `502 github_unavailable` です。

Web 用の OAuth App は任意です（`GITHUB_WEB_CLIENT_ID`・`GITHUB_WEB_CLIENT_SECRET`・`GITHUB_WEB_REDIRECT_URI` を 3 つそろえて設定したときだけ使えます）。今の Web の OAuth App をそのまま使えます。GitHub は登録した callback URL の下の階層を `redirect_uri` に使えるので、Web の callback は `https://<Web>/api/auth/callback/github/go`（既存の callback の下）にしてあり、OAuth App の設定を変える必要はありません。この場合、PKCE と state は Web（Next.js）が作り、API は `code` の交換だけを行います。

## ゲスト

`POST /v1/auth/guest` は、認証なしでゲストのトークン一式を返します。本文は空か `{}` です。`role` は `guest`、`ownerId` は `guest` で、トークンの形は他の役割と同じです（`login` と `sv` は持ちません）。

- ゲストのトークンで呼べるのは `GET /v1/me` だけです。ほかの認証つきルートは `403 forbidden` を返します。
- ゲストのリフレッシュトークンの寿命は **24 時間** です（admin・会員は 30 日）。誰でも作れるので、DB の行を増やされにくいよう短くしています。ゲストがログインするたびに、期限切れの行を削除します。
- 失効の確認は常に通ります（許可リストも `sessionVersion` もありません）。リフレッシュ・ログアウトは他の役割と同じです。
- `POST /v1/auth/guest` には、他のログインと同じレート制限があります。

## パスワードログイン（会員）

`POST /v1/auth/password` に `{loginId, password}` を送ります。規則は Web の `AuthenticatePasswordAccount` と同じです。

- `loginId` は前後の空白を除いて小文字にし（JavaScript の `trim` と `toLowerCase` と同じ規則。たとえば「İ」（U+0130）は「i」と結合文字になるので、検証で落ちます）、`^[a-z0-9._-]{3,32}$` に一致すること。`password` は 1〜128 文字。
- 試行回数には、クライアントのアドレスごとの制限があります（下の [パスワードログインの試行回数](#試行回数の制限)）。超えると、パスワードのハッシュを計算せずに `429 rate_limited` を返します。アカウントごとのロックはありません。
- 形式の不正・存在しない ID・パスワード違いは、**すべて同じ `401 unauthorized`** です。どの経路でも scrypt を 1 回計算するので（存在しない ID などはダミーのハッシュで計算します）、応答の内容からも時間からも区別できません。
- パスワードのハッシュは Web と同じ `scrypt:N:r:p:salt:key` 形式です（N ≤ 2^15・r ≤ 8・p ≤ 4 を超えるものは拒否し、比較は定数時間）。scrypt は 1 回に 32 MiB を使うため、タスクごとに同時に 4 件までしか計算しません。

## トークン

ログイン・リフレッシュの応答は次の形です。

```json
{
  "accessToken": "eyJhbGciOiJIUzI1NiIs…",
  "refreshToken": "q3b8…",
  "expiresIn": 900
}
```

### アクセストークン（15 分）

HS256 で署名した JWT です。`expiresIn` はその有効期限（秒）で、常に `900` です。

| クレーム | 内容                                                                                                               |
| -------- | ------------------------------------------------------------------------------------------------------------------ |
| `iss`    | `ffpf-zhuelog-api`（固定）                                                                                         |
| `aud`    | `ffpf-zhuelog-mobile`（固定）                                                                                      |
| `sub`    | `ownerId`                                                                                                          |
| `role`   | `admin`・`member`・`guest`                                                                                         |
| `iat`    | 発行時刻                                                                                                           |
| `exp`    | 有効期限（発行から 15 分）                                                                                         |
| `login`  | admin だけ（ゲストにも付けない）。ログイン時の GitHub のログイン名（情報として残すだけで、許可の判定には使わない） |
| `sv`     | member だけ。発行時の `PasswordAccount.sessionVersion`                                                             |

認証が必要なエンドポイントには `Authorization: Bearer <accessToken>` を付けます。API は毎回、署名・`iss`・`aud`・`exp`・`iat` を確かめ、さらに次の **失効の確認** を行います。`aud` は Web とモバイルで同じです。

`GET /v1/me` は、トークンの持ち主の `{ownerId, role, login, displayName?, accountId?}` を返します（[リファレンス](../reference/auth.md#get-v1-me)）。会員の `displayName` と `accountId` は DB から読みます。

### リフレッシュトークン（30 日。ゲストは 24 時間）

- ランダムな 32 バイトの base64url です。DB（`ApiRefreshToken`）には SHA-256 のハッシュだけを保存します。
- ログインのたびに新しい **ファミリー**（`familyId`）が始まり、リフレッシュで発行されるトークンは同じファミリーに属します。
- アクセストークンが切れたら（`401` が返ったら）、`POST /v1/auth/refresh` に `{refreshToken}` を送って新しい組を受け取ります。

## ローテーションと再利用の検知

`POST /v1/auth/refresh` を呼ぶと、提示したリフレッシュトークンは失効し（`revokedAt`）、同じファミリーの新しい組が返ります。失効と発行は 1 つのトランザクションで行います。**リフレッシュトークンは 1 回しか使えません**。応答の `refreshToken` で手元の値を必ず置き換えてください。

| 提示されたトークン                                     | 結果                                                  |
| ------------------------------------------------------ | ----------------------------------------------------- |
| 有効（未失効・期限内・失効の確認に通る）               | 200。新しい組を返し、古いトークンを失効させる         |
| 未知のトークン・空                                     | 401                                                   |
| 期限切れ                                               | 401                                                   |
| **30 秒より前に失効したトークン（使用済み）**          | **盗用とみなしてファミリー全体を失効させ**、401       |
| 失効から 30 秒以内で、ファミリーに有効なトークンがある | 200。同じファミリーに新しい組を出す（猶予。下を参照） |
| 失効から 30 秒以内でも、ファミリーが失効済み           | ファミリー全体を失効させ、401                         |
| 失効の確認に通らない（パスワード変更・許可リスト外し） | ファミリー全体を失効させ、401（許可リスト外しは 403） |

使用済みのトークンが再び現れたら、正規のアプリと攻撃者のどちらかが古い値を持っていることになるので、ファミリーごと無効にして両方にログインし直してもらいます。

### リフレッシュの猶予

ブラウザは同時に複数の要求を出すので、同じリフレッシュトークンで同時にリフレッシュが起こります。2 本目を使用済みとして扱うと、ファミリーごと失効して利用者がログアウトされます。そこで、ローテーションから **30 秒以内** に、同じファミリーに有効なトークンが残っているときは、失効させずに同じファミリーで新しい組を返します（失効の確認は同じように行います）。この判定とトークンの追加は、ファミリー単位のロックの中で行うので、ログアウトや再利用の検知と同時に起こっても、失効したファミリーに新しいトークンが残ることはありません。

30 秒を過ぎた古いトークン、またはファミリーが失効済みのとき（ログアウト・再利用の検知の後）は、今までどおりです。

**残るリスク**：盗まれたトークンが、本人のリフレッシュと同じ 30 秒のうちに使われると、再利用として検知されません（どちらも新しい組を受け取ります）。猶予の 30 秒は固定です。

`POST /v1/auth/logout` は `{refreshToken}` のファミリーを失効させて `204` を返します。未知のトークンや空でも `204` です。ログアウトしてもアクセストークンは期限（最長 15 分）まで有効なので、アプリは手元のトークンを捨ててください。

DB の掃除は cron を使わず、ログインに成功したときにその `ownerId` の行だけを対象に行います。期限切れの行は削除し、失効済みの行は、同じファミリーに未失効かつ期限内の行が残っていない場合に限って削除します（生きているファミリーの失効済みトークンを残すことで、再利用の検知が効き続けます）。

## 失効：`sessionVersion` と許可リスト

アクセストークンは 15 分で切れますが、それを待たずに使えなくする仕組みがあります。アクセストークンの検証（毎リクエスト）とリフレッシュのたびに、同じ確認を行います。

| 役割     | 確認すること                                                                                  | 通らないとき |
| -------- | --------------------------------------------------------------------------------------------- | ------------ |
| `admin`  | トークンの `sub`（GitHub の数値 ID）が **今の** 許可リスト（`AUTH_ALLOWED_GITHUB_IDS`）にある | `403`        |
| `member` | `PasswordAccount` が存在し、その `sessionVersion` がトークンの `sv` と一致する                | `401`        |

`sessionVersion` は次の操作で 1 上がり、その会員の **Web と API の既存のログインがすべて** 無効になります。

- 会員が自分のパスワードを変えたとき（`POST /v1/account/password`。操作した端末も含めて無効になるので、アプリはログインし直します）
- admin が会員のパスワードをリセットしたとき（Web の管理画面、または `POST /v1/admin/accounts/{id}/password`）

admin を許可リストから外すと、その admin のトークンは期限前でも `403` になり、リフレッシュもできなくなります（ファミリーは失効します）。許可リストは起動時に読むので、変えたら API を再デプロイします。

## レート制限

次のエンドポイントには、IP ごとに **1 分あたり 10 回** の制限があります。6 つは同じ枠を共有します。

- `POST /v1/auth/github`
- `POST /v1/auth/guest`
- `POST /v1/auth/password`
- `POST /v1/auth/refresh`
- `POST /v1/auth/logout`
- `POST /v1/account/password`（認証より前に数えるので、無効なトークンでの呼び出しも数に入ります）

超えると `429 rate_limited` です。固定の 1 分の窓で、窓が変われば回数は戻ります。

- 数えるのはインスタンスごとのメモリ上です。Vercel がインスタンスを増やすと、実際の上限はその分ゆるくなります。パスワードの総当たりは、DB で数える [試行回数の制限](#試行回数の制限) でも防いでいます。
- Web（Next.js）から呼ばれたときは、全員が Vercel の関数の 1 つの IP に見えてしまいます。そこで Web は、利用者の IP を `X-Zhuelog-Client-IP` で、共有の秘密（`API_WEB_PROXY_SECRET`、32 バイト以上）を `X-Zhuelog-Proxy-Secret` で送ります。API は秘密が **一致したときだけ**（定数時間で比べます）`X-Zhuelog-Client-IP` を IP として使います。一致しないとき、`API_WEB_PROXY_SECRET` が未設定のときは、このヘッダーを無視します。この IP は、下の [試行回数の制限](#試行回数の制限) にも使います。
- それ以外では、IP に `X-Forwarded-For` の **最後の値** を使い、無ければ接続元のアドレスを使います。Vercel はこのヘッダーをクライアントの IP で上書きするので偽装されません。Vercel の前に別のプロキシを置くと制限が正しく働かないので、置かないでください。
- それ以外のエンドポイントにレート制限はありません。

## 試行回数の制限

パスワードログイン（`POST /v1/auth/password`）には、上のレート制限とは別に、DB の `SignInThrottle` テーブルで数える試行回数の制限があります。Web と同じテーブル・同じキーを使うので、同じクライアントからの Web と API の試行は合わせて数えられます。

| 数える単位                         | 上限（15 分の固定の枠） | 回数が戻るとき                                                  |
| ---------------------------------- | ----------------------- | --------------------------------------------------------------- |
| 同じクライアント                   | 20 回                   | 枠が終わったとき                                                |
| 同じクライアントから同じ `loginId` | 5 回                    | 枠が終わったとき、またはその `loginId` でログインに成功したとき |

- 超えると、パスワードのハッシュを計算せずに `429 rate_limited` を返します。止まったときは、枠が終わるまで（最長 15 分）待ちます。
- クライアントごとの回数は、形式の不正な入力も含めて、すべての試行で数えます。`loginId` ごとの回数は、`loginId` の形式が正しい試行だけで数えます。アカウントが存在するかどうかには関係なく数えるので、回数からアカウントの有無はわかりません。
- 回数は必ずクライアントのアドレスごとに数えます。他人が別の場所から間違ったパスワードを繰り返しても、本人のログインは止まりません（以前のアカウントごとのロックは廃止しました）。
- アドレスは、レート制限と同じ決め方（`X-Zhuelog-Client-IP` を信頼できるときはその値、そうでなければ `X-Forwarded-For` の最後の値、それも無ければ接続元）で、IPv4 はそのまま、IPv6 は上位 64 ビット（/64）単位で数えます。

自分のパスワードの変更（`POST /v1/account/password`）にも、アカウントごとに 15 分で 5 回までの制限があります。超えたときは、今のパスワードが違うときと同じ `400 invalid_current_password` を返します。変更に成功すると回数は戻ります。この回数はパスワードの変更だけのもので、ログインには影響しません。
