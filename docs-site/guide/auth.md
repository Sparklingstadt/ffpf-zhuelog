# 認証

API の利用者は 2 種類です。ログインに成功すると、どちらも同じ形のトークンの組（アクセストークンとリフレッシュトークン）を受け取ります。

| 役割（`role`） | ログイン方法                       | `ownerId`（ノートの所有者 ID）          |
| -------------- | ---------------------------------- | --------------------------------------- |
| `admin`        | GitHub（PKCE）。許可リストに載る人 | GitHub の数値 ID（例：`12345678`）      |
| `member`       | ログイン ID とパスワード           | `password:` + `PasswordAccount` の `id` |

`ownerId` は Web と同じ値で、ノートやフォローの所有者を表します。

## GitHub ログイン（admin）

```text
アプリ ──(1) 認可画面を開く（PKCE S256）──▶ GitHub
アプリ ◀─(2) カスタム URL スキームで code ── GitHub
アプリ ──(3) POST /v1/auth/github {code, codeVerifier, redirectUri}──▶ API
API    ──(4) code + code_verifier + client_secret を交換、GET /user──▶ GitHub
アプリ ◀─(5) {accessToken, refreshToken, expiresIn} ── API
```

1. アプリは PKCE（S256）で GitHub の認可画面を開き、モバイル用 OAuth App のカスタム URL スキームで `code` を受け取ります。
2. `POST /v1/auth/github` に `{code, codeVerifier, redirectUri}` を送ります。`redirectUri` は API の `GITHUB_MOBILE_REDIRECT_URI` と完全に一致していなければなりません。
3. API は `client_secret` と `code_verifier` を付けて GitHub のトークンエンドポイントで `code` を交換し、`GET /user` で数値 ID とログイン名を得ます。GitHub への通信はそれぞれ 10 秒でタイムアウトします。GitHub のアクセストークンは保存しません。
4. ログイン名を前後の空白を除いて小文字にし、許可リストと照合します。含まれなければ `403 forbidden` です。
5. `ownerId` を GitHub の数値 ID、`role` を `admin` としてトークンを発行します。

`code`・`codeVerifier`・`redirectUri` を GitHub が拒否したとき（`bad_verification_code` など）や `redirectUri` が一致しないときは `401 unauthorized`、GitHub に届かない・応答が不正なときは `502 github_unavailable` です。

## パスワードログイン（会員）

`POST /v1/auth/password` に `{loginId, password}` を送ります。規則は Web の `AuthenticatePasswordAccount` と同じです。

- `loginId` は前後の空白を除いて小文字にし、`^[a-z0-9._-]{3,32}$` に一致すること。`password` は 1〜128 文字。
- ログインを試すたびに、失敗回数を 1 つの UPDATE 文でアトミックに予約します。**5 回失敗すると 15 分ロック** され、ロック中は正しいパスワードでも失敗します。ロックが切れていれば回数は 1 から数え直し、成功すると失敗回数とロックが消えます。
- 形式の不正・存在しない ID・ロック中・パスワード違いは、**すべて同じ `401 unauthorized`** です。どの経路でも scrypt を 1 回計算するので（存在しない ID などはダミーのハッシュで計算します）、応答の内容からも時間からも区別できません。
- パスワードのハッシュは Web と同じ `scrypt:N:r:p:salt:key` 形式です（N ≤ 2^15・r ≤ 8・p ≤ 4 を超えるものは拒否し、比較は定数時間）。scrypt は 1 回に 32 MiB を使うため、タスクごとに同時に 4 件までしか計算しません。

## トークン

ログイン・リフレッシュの応答は次の形です。

```json
{
  "accessToken": "eyJhbGciOiJIUzI1NiIs…",
  "refreshToken": "q3b8…",
  "expiresIn": 900
}
```

### アクセストークン（15 分）

HS256 で署名した JWT です。`expiresIn` はその有効期限（秒）で、常に `900` です。

| クレーム | 内容                                                   |
| -------- | ------------------------------------------------------ |
| `iss`    | `ffpf-zhuelog-api`（固定）                             |
| `aud`    | `ffpf-zhuelog-mobile`（固定）                          |
| `sub`    | `ownerId`                                              |
| `role`   | `admin` か `member`                                    |
| `iat`    | 発行時刻                                               |
| `exp`    | 有効期限（発行から 15 分）                             |
| `login`  | admin だけ。GitHub のログイン名                        |
| `sv`     | member だけ。発行時の `PasswordAccount.sessionVersion` |

認証が必要なエンドポイントには `Authorization: Bearer <accessToken>` を付けます。API は毎回、署名・`iss`・`aud`・`exp`・`iat` を確かめ、さらに次の **失効の確認** を行います。

### リフレッシュトークン（30 日）

- ランダムな 32 バイトの base64url です。DB（`ApiRefreshToken`）には SHA-256 のハッシュだけを保存します。
- ログインのたびに新しい **ファミリー**（`familyId`）が始まり、リフレッシュで発行されるトークンは同じファミリーに属します。
- アクセストークンが切れたら（`401` が返ったら）、`POST /v1/auth/refresh` に `{refreshToken}` を送って新しい組を受け取ります。

## ローテーションと再利用の検知

`POST /v1/auth/refresh` を呼ぶと、提示したリフレッシュトークンは失効し（`revokedAt`）、同じファミリーの新しい組が返ります。失効と発行は 1 つのトランザクションで行います。**リフレッシュトークンは 1 回しか使えません**。応答の `refreshToken` で手元の値を必ず置き換えてください。

| 提示されたトークン                                     | 結果                                                  |
| ------------------------------------------------------ | ----------------------------------------------------- |
| 有効（未失効・期限内・失効の確認に通る）               | 200。新しい組を返し、古いトークンを失効させる         |
| 未知のトークン・空                                     | 401                                                   |
| 期限切れ                                               | 401                                                   |
| **すでに失効したトークン（使用済み）**                 | **盗用とみなしてファミリー全体を失効させ**、401       |
| 同時に 2 回使われ、もう一方のローテーションに負けた    | ファミリー全体を失効させ、401                         |
| 失効の確認に通らない（パスワード変更・許可リスト外し） | ファミリー全体を失効させ、401（許可リスト外しは 403） |

使用済みのトークンが再び現れたら、正規のアプリと攻撃者のどちらかが古い値を持っていることになるので、ファミリーごと無効にして両方にログインし直してもらいます。

`POST /v1/auth/logout` は `{refreshToken}` のファミリーを失効させて `204` を返します。未知のトークンや空でも `204` です。ログアウトしてもアクセストークンは期限（最長 15 分）まで有効なので、アプリは手元のトークンを捨ててください。

DB の掃除は cron を使わず、ログインに成功したときにその `ownerId` の行だけを対象に行います。期限切れの行は削除し、失効済みの行は、同じファミリーに未失効かつ期限内の行が残っていない場合に限って削除します（生きているファミリーの失効済みトークンを残すことで、再利用の検知が効き続けます）。

## 失効：`sessionVersion` と許可リスト

アクセストークンは 15 分で切れますが、それを待たずに使えなくする仕組みがあります。アクセストークンの検証（毎リクエスト）とリフレッシュのたびに、同じ確認を行います。

| 役割     | 確認すること                                                                    | 通らないとき |
| -------- | ------------------------------------------------------------------------------- | ------------ |
| `admin`  | トークンの `login` が **今の** 許可リスト（`AUTH_ALLOWED_GITHUB_LOGINS`）にある | `403`        |
| `member` | `PasswordAccount` が存在し、その `sessionVersion` がトークンの `sv` と一致する  | `401`        |

`sessionVersion` は次の操作で 1 上がり、その会員の **Web と API の既存のログインがすべて** 無効になります。

- 会員が自分のパスワードを変えたとき（`POST /v1/account/password`。操作した端末も含めて無効になるので、アプリはログインし直します）
- admin が会員のパスワードをリセットしたとき（Web の管理画面、または `POST /v1/admin/accounts/{id}/password`）

admin を許可リストから外すと、その admin のトークンは期限前でも `403` になり、リフレッシュもできなくなります（ファミリーは失効します）。許可リストは起動時に読むので、変えたら API を再デプロイします。

## レート制限

次のエンドポイントには、IP ごとに **1 分あたり 10 回** の制限があります。5 つは同じ枠を共有します。

- `POST /v1/auth/github`
- `POST /v1/auth/password`
- `POST /v1/auth/refresh`
- `POST /v1/auth/logout`
- `POST /v1/account/password`（認証より前に数えるので、無効なトークンでの呼び出しも数に入ります）

超えると `429 rate_limited` です。固定の 1 分の窓で、窓が変われば回数は戻ります。

- 数えるのはタスク（インスタンス）ごとのメモリ上です。タスクが 2 つあれば、実際の上限はその分ゆるくなります。パスワードの総当たりは、DB 側のロック（5 回失敗で 15 分）でも防いでいます。
- IP には `X-Forwarded-For` の **最後の値**（ALB が付けた値）を使い、無ければ接続元のアドレスを使います。ALB を通らずにタスクへ届く経路を作ると制限が正しく働かないので、作らないでください。
- それ以外のエンドポイントにレート制限はありません。
