## 2. `POST /v1/line/webhook`

`lineWebhook` (line_handlers.go:71-101), in this order:

1. `start := now()`.
2. Read the whole body (`io.ReadAll`) under the global 1 MiB limit (`limitBody` middleware.go:18,131) — over it → **413** `too_large` 「リクエストが大きすぎます。」 (`TestWebhookOversizedBodyIs413` :278-283); another read error → 400.
3. `line.VerifySignature(channelSecret, body, X-Line-Signature)` false → **401** `unauthorized` 「認証が必要です。」 (`TestWebhookRejectsMissingOrWrongSignature` :146-164). Nothing is parsed before this.
4. `extendLineDeadlines` (:56-61): read/write deadlines 60 s from now (the server's are 30 s) — only after the signature passed.
5. `line.ParseWebhook(body)` error → **400** `invalid_request` 「リクエストが不正です。」 (`TestWebhookMalformedSignedBodyIs400` :271-276).
6. `ctx = WithTimeout(WithoutCancel(r.Context()), 55 s)` (`webhookEventsTimeout` :43): LINE or the edge dropping the connection does not cancel the work; the whole delivery has 55 s (`TestWebhookEventsRunWithoutTheRequestCancellationAndWithATimeout` :237-269).
7. `deadline := start + 45 s` (`webhookDeliveryBudget` :48), the **same** deadline for every event (`TestWebhookGivesEveryEventTheSameDeliveryDeadline` :217-235).
8. Events one after another (`svc.HandleEvent(ctx, ev, deadline)`); an error is logged as `Warn("line event failed", "event_id", ev.WebhookEventID)` (never the error text) and the loop goes on (`TestWebhookAnswers200WhenAnEventFailsAndKeepsGoing` :191-215).
9. **200** `{}` whatever happened to the events, so LINE never redelivers (LINE's "verify" delivery `{"events":[]}` → 200, `TestWebhookVerifyDeliveryWithNoEvents` :166-177).

So Go answers **after** the work, inline — there is no queue for the webhook. A text that cannot be finished in the delivery stays `pending` in `LineMessage` and the daily cron (§10) finishes it. `isRedelivery` (`deliveryContext`) is **not read**; idempotency comes only from the unique `LineMessage.webhookEventId` (§6).

### Signature (`line/signature.go:14-25`)

- false when the secret is empty or the header is `""`.
- The header is decoded with `base64.StdEncoding` (padded standard alphabet; a decode error → false), then `hmac.Equal(decoded, HMAC-SHA256(secret, rawBody))` (constant time). The secret is the trimmed `LINE_CHANNEL_SECRET` as bytes.
- `TestVerifySignature` signature_test.go:16-43: valid; body differing by one byte; wrong secret; empty header; not base64 (`!!!not-base64!!!`); truncated signature (last 4 chars cut); empty secret with a signature made from the empty secret → all false but the first.
- Go's standard decoder ignores `\r`/`\n` and accepts non-canonical trailing bits; a header never contains those, so comparing the canonical Base64 string of the HMAC is equivalent.

### Parsing (`line/webhook.go:34-57`)

- `json.Unmarshal` into `{events: [{type, webhookEventId, replyToken, source: {type, userId}, message: {type, text}}]}`. Unknown fields are ignored. A JSON syntax error, a top level that is not an object (or `null`), `events` that is not an array (or `null`), an element that is not an object (or `null`), or a read field of the wrong JSON type → error → 400. `null` or a missing field is the zero value (`""`, empty object).
- Only `type == "message"` events are kept; the result is never nil (`[]` for no events).
- `Event{WebhookEventID, ReplyToken, UserID: source.userId, IsText: message.type == "text", FromUser: source.type == "user", Text: message.text only when IsText}`.
- Tests line/webhook_test.go:8-82 (empty events, missing events, text from user, group and room not from user, sticker not text, only message events kept, malformed).

## 4. Link codes

**Issue** (`POST /v1/line/link-code` → `IssueCode` linebot/code.go:35-52):

- Role member or admin, else `ErrForbidden`.
- 8 random bytes (`crypto/rand`), each mapped to `codeAlphabet[b % 32]`, alphabet `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` (no 0, O, 1, I; 32 divides 256 so no bias).
- `expiresAt = now + 10 min`; store `PutLineLinkCode(ownerID, role, sha256hex(code), expiresAt)` (§12), which **replaces** the owner's previous code.
- Answer **200** `{"code":"ABCD2345","expiresAt":"<UTC ISO ms>"}`. The code is never logged and only its SHA-256 (lowercase hex) is stored.
- Tests code_test.go:23-101 (`TestIssueCode`, `…Admin`, `…UsesRandomSource`, `…RandomFailure`, `…GuestForbidden`).

**Shape** (`codeShape` code.go:61-72): `strings.ToUpper(strings.TrimSpace(norm.NFKC.String(text)))`; a code iff exactly 8 runes, all in the alphabet. `TestNormalizeCode` :121-147: `ABCD2345`, `abcd2345`, `ＡＢＣＤ２３４５`, `　ａｂｃｄ２３４５　` → `ABCD2345` true; `ABCD234` (7), `ABCD23456` (9), `ABCD2340`, `ABCD2341`, `ABCDO345`, `ABCDI345`, `ABCD 345`, `你好你好你好你好`, `""` → false.

**Redeem** (`redeem` code.go:76-100):

1. `ConsumeThrottle("line-link:" + UserID, 5, 1 h)` (`throttleLimit`/`throttleWindow` :29-30; `SignInThrottle`, store/throttle.go — the same two statements the web already runs in `src/infrastructure/prisma/sign-in-throttle-store.ts`). Every attempt counts, successful ones too. Error → return it. Over → reply `MsgThrottled` with no store lookup (`TestLinkThrottledOnSixthAttempt` :196-222, `TestLinkThrottleWindowAndLimit` :224-236).
2. `RedeemLineLinkCode(sha256hex(code), UserID, now)` (§12): unknown or expired → reply `MsgBadCode` (the attempt stays counted, `TestLinkExpiredCode` :179-194).
3. `ResetThrottle(key)`; a failure is only logged (`Warn("line throttle reset failed", "event_id")`).
4. Reply `MsgRelinked` when this LINE account was linked before (to anyone), else `MsgLinked` (`TestRelink` :249-265, `TestLinkWithNormalizedCodes` :153-177). The new link's `reviewNotify` is the default `false` (a new row).

## 8. LINE Messaging API (line/client.go, line/quota.go)

- `Reply(token, texts…)` → `POST {base}/v2/bot/message/reply` `{"replyToken": token, "messages": [{"type":"text","text": t}…]}`; `Push(to, texts…)` → `POST {base}/v2/bot/message/push` `{"to": to, "messages": […]}` (client.go:37-44). Headers `Content-Type: application/json`, `Authorization: Bearer <LINE_CHANNEL_ACCESS_TOKEN>`. 1..5 messages per call, else an error before any request (`TestMessageCountLimits` client_test.go:128-144). The body is drained (≤ 1 MiB) and never surfaced; any non-2xx → `line: api returned status N`; a transport error → `line: request failed` — errors never contain the token, reply token, recipient or text (`TestStatusErrorsDoNotLeakSecrets` :96-110, `TestTransportErrorDoesNotLeakSecrets` :112-126). 10 s, no redirects. A trailing slash on the base URL is fine (:85-94).
- Reply tokens are valid once, for about a minute; replies are free. Pushes count against the month's allowance (200 a month on the free plan).
- `PushQuota` (quota.go:23-48): `GET /v2/bot/message/quota` → `{"type":"none"}` = unlimited; `{"type":"limited","value":N}` → then `GET /v2/bot/message/quota/consumption` → `{"totalUsage":U}` (missing → error); `Remaining = max(N − U, 0)`; any other type → error. `TestPushQuota`, `TestPushQuotaFailures` quota_test.go:30-60.

## 20. Running Go and the web side by side (why the order is safe)

- Both sides use the same tables with the same meanings: `LineLinkCode` keyed by the SHA-256 hex of the upper-case code; `LineLink` with `role` and `reviewNotify`/`reviewNotifiedOn`; `LineMessage` statuses, attempts (max 2) and the text cleared when done or failed; `SignInThrottle` key `line-link:<lineUserId>`; `AiUsage.feature = "line"`. So a code the web issues is redeemed by Go's webhook, Go's drain finishes rows the web's webhook left pending, and Go's review message reads the setting the web writes — as long as the web keeps these exactly.
- Only one webhook receives LINE (the URL in LINE Developers), so replies never double. Two drains at once cannot double a reply either: `StartLineMessageAttempt` and `ClaimReviewNotify` are single conditional `UPDATE`s, and `CompleteLineMessage` rolls back when the row is no longer pending. A row with `attempts = 0` (deferred) could still be generated twice by two concurrent drains (the second `UPDATE` sees `attempts = 1 < 2`) — one OpenAI call wasted, one note, one push. The 4-step order of the design avoids two crons at once.
- Until Go is redeployed from the merged main, the production Go keeps its LINE routes and both crons.
