# 就職までのロードマップ

学习録を、個人開発のアプリから、フルスタックの Web エンジニアの職に応募するときの中心になるポートフォリオにし、2027 年 1〜3 月に応募を始めるまでの道筋です。機能の順番は [ロードマップ](roadmap.md) と同じ「今」「次」「いつか」の 3 段で並べ、各段の終わりに「次へ進むかを決める基準」を置きます。

この文書は、2026 年 11 月 9 日まであった「収益化までのロードマップ」を書き換えたものです。学习録は商用利用しないと決めたので（Vercel は Hobby のまま）、売るための項目は外し、見せるための項目に置き換えました。前の文書は git の履歴（コミット 08bed36 の `docs/monetization-roadmap.md`）にあります。収益化のために作った AI の利用量の記録（v0.26.0）は、費用を測って判断した例として、そのまま見せる材料に使います。

ここに書いた時期・数は、2026 年 11 月時点の見込みです。進んだら書き換えます。

## 3 つの節目

| 節目          | 意味                                                                         | 目安                                                                        |
| ------------- | ---------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| 1. 見せられる | 学习録を知らない人が、リポジトリと本番を 10 分見て、何をどう作ったかが分かる | README・設計の文書・触れる経路がそろい、第三者 1 人に確かめてもらう         |
| 2. 応募できる | 書類がそろい、1 社目に出す                                                   | 職務経歴書に学习録の章があり、GitHub のプロフィールから学习録にたどり着ける |
| 3. 内定       | 学习録を見た会社から内定が出る                                               | 1 件                                                                        |

節目 2 までが、このロードマップの範囲です。節目 3 は、応募を始めてから面接の結果を見て書き足します。

## いまの立ち位置

- **公開リポジトリで、本番が動いている**：GitHub は public で、本番は <https://ffpf-zhuelog.sparklingstadt.com/> です。2026 年 9 月 20 日から 275 コミット、リリースノートは 30 本（v0.30.0 まで）あります。
- **テストがある**：TypeScript の単体テスト 360 件、Playwright の E2E 190 件（PC とスマホの 2 つの幅）、Go のテストファイル 81 本（Postgres を使うものを含む）が、push のたびに lefthook で走ります。GitHub Actions は 2026 年 11 月の分を使い切っていて、CI は止まっています。
- **設計の記録がある**：README に層の構成（domain / application / infrastructure / presentation / composition）、`docs/superpowers/specs/` と `plans/` に機能ごとの設計と計画、`docs/security-review-2026-09-24.md` にセキュリティの見直しがあります。ただし、全体を 1 つにまとめた文書はなく、README は機能の説明が 30 節以上並んでいて、入口としては長すぎます。
- **知らない人は触れない**：ID・パスワードのアカウントは管理者が発行し、セルフ登録はありません。ゲストは介詞・補語・量詞の練習だけ使えます。学習ノート・復習・単語帳・LINE・AI は、採用担当が自分で試せません。
- **リポジトリの顔が古い**：GitHub の説明文は「ピン音」のまま（v0.30.0 で「ピンイン」にそろえました）、homepage は `ffpf-zhuelog.vercel.app`、トピックは空、LICENSE はありません。
- **お金は AI だけにかかる**：LINE の添削・翻訳、ChatGPT と話す、クイック質問、単語帳の下書きが OpenAI を呼びます。だれが・どの機能で・トークンをいくつ使ったかは `/admin/ai-usage` で月ごとに見られます（2026 年 11 月 9 日から記録）。ほかは Vercel Hobby・Neon・LINE の無料枠とドメイン代だけで動きます。

## 方針

1. **学习録 1 本に絞ります。** 新しいアプリは作りません。1 本を深く見せるほうが、浅いものを並べるより伝わります。
2. **「作った」ではなく「判断した」を見せます。** Web と Go API を分けた理由、認証を 3 通りにした理由、FSRS を選んだ理由、HSK の級を 2 通りの決め方にした理由、AI の費用を測ってから料金を考えた経緯など、選んだ理由と捨てた案を文書にします。
3. **本番で動いているものを、ログインなしで触れるようにします。** 採用担当はアカウントの発行を待ってくれません。
4. **機能追加より仕上げを優先します。** [ロードマップ](roadmap.md) の 15 以降は、応募書類に「こう直した」と書ける小さなもの（15、16、17）だけ先に進め、大きなもの（5、12 の残り）は応募が落ち着くまで止めます。
5. **商用利用はしません。** Vercel は Hobby のままです。有料プラン・決済・規約の整備はこのロードマップにありません。

## 今（Now）：見せられる状態にする（〜2026 年 12 月）

いまのユーザーに影響を与えずにできる、仕上げです。

### J1. リポジトリの入口を整える

- README の冒頭を、次の順の 1 画面に作り直します：何のアプリか（1 文）、画面のスクリーンショット 3 枚（学習ノート、練習、今日の復習。PC とスマホ）、技術構成、設計の要点へのリンク（J3）、試し方（J2）。いまの 30 節以上の機能の説明は `docs/features.md` のような別の文書へ移し、README からリンクします。
- GitHub の説明文を「ピンイン」に直し、homepage を `https://ffpf-zhuelog.sparklingstadt.com/` にし、トピック（`nextjs`、`go`、`postgresql`、`chinese-learning`、`spaced-repetition` など）を付けます。
- LICENSE を決めて置きます（「決めていないこと」）。
- GitHub のプロフィールに README を作り、学习録を 1 番目に載せます。

### J2. 採用担当がログインなしで触れる経路を作る

候補は 2 つで、どちらにするかは「決めていないこと」に書きました。

- **デモアカウント**：`/signin` に「デモで試す」を置き、読み取り中心のアカウント（学習ノート・復習・単語帳・会話ノートに seed のデータが入っている）に入れます。AI の機能は呼べないか、1 日の回数を小さく制限します。データは毎晩 Cron で seed に戻します。
- **動画と画面**：ログイン後の画面を 2〜3 分の動画（または GIF の連なり）にして、README と LP（`/`）のログイン前の案内に置きます。

ゲストで使える練習（介詞・補語・量詞、HSK の級の切り替え、スマホでの表示）は、いまのままで見せられます。

### J3. 設計を 1 つの文書にまとめる

`docs/architecture.md` を書きます。見出しは次のとおりです。

1. 全体の図（ブラウザー、Next.js、Go API、Postgres、OpenAI、LINE、FFPF ID）
2. Web と Go API を分けた理由と、Web が DB を読まない決まり
3. 層の構成と、依存の向き（README の節を移す）
4. 認証：GitHub OAuth・ID とパスワード・FFPF ID（OIDC）・ゲストと、Go API の JWT と refresh token
5. 復習：FSRS を選んだ理由、`ReviewItem` の列に状態を持つ理由、ノート・練習・単語帳を同じ列に載せた理由
6. 練習：4 択の共通部品、記録の表の共有（`mode`）、HSK の級の 2 通りの決め方と最長一致
7. LINE：Webhook を受けて非同期に処理する流れ、やり直し、送信数の枠
8. AI：OpenAI を呼ぶ 4 か所、利用量の記録、費用を測ってから料金を考えた経緯（旧ロードマップの M1〜M4）
9. テスト：単体・Go・E2E の分担、E2E が Docker の Postgres と OpenAI のスタブで動く理由
10. 捨てた案と、いまの課題（例：Web と Go で重複している入力の検証、CSV の取り込みの移行）

`docs/superpowers/specs/` と `plans/` は、この文書から「詳しくはこちら」でリンクします。

### J4. 品質を外から見えるようにする

- CI を戻します。2026 年 12 月に GitHub Actions の枠が戻ったら、push ごとに走るのは lint・型・単体・Go だけにし、E2E は PR と main だけにして、月の枠に収まるようにします。README にバッジを置きます。
- Lighthouse（性能・アクセシビリティ）を主な 4 ページで測り、数字と直したことを `docs/quality.md` に残します。
- テストの数と走り方を README の「試し方」に 3 行で書きます。

### J5. 使われている証拠を集める

- 自分以外の会員が、月に何日使ったかを数えます（収益化の基準にあった「月 4 日以上使う人が 3 人以上」は、ここでは目標ではなく、書類に書く事実として使います）。
- AI の利用量（`/admin/ai-usage`）の 1 か月分を、「1 文の添削はいくら」のように費用の数字にします。
- 使っている人に 3 つだけ聞きます：続けて使う理由、使わなくなった機能、困ったこと。答えは J3 の「いまの課題」と、面接で話す材料にします。

## 次（Next）：応募する（2027 年 1〜3 月）

### J6. 職務経歴書と学习録の章

- 学习録の章は「課題 → 設計 → 結果」の順で 1 ページにします。結果は数字で書きます：コミット数、リリース数、テストの件数、本番の稼働期間、会員の利用日数、AI の 1 文あたりの費用。
- 設計の判断を 3 つ選び、それぞれ「選んだ理由・捨てた案・あとで分かったこと」を 3 行で書きます。候補は J3 の 2・5・8 です。
- 技術の一覧は、学习録で実際に使ったものだけにします（Next.js 16 App Router / Server Actions、TypeScript、Go、PostgreSQL、Prisma、Playwright、Tailwind、Vercel、Neon、OpenAI API、LINE Messaging API、OIDC）。
- 学习録以外の経歴は、この文書の範囲外です。「決めていないこと」に書いた条件と合わせて、別に書きます。

### J7. 外から見える書き物

- 技術記事を 2〜3 本書きます。候補：
  - Next.js の Web と Go API を分けて、Web が DB を読まないようにした話
  - FSRS で、学習ノート・練習の間違い・単語帳を 1 つの復習の列に載せた話
  - 公式の HSK 3.0 の語彙表で練習の文の級を決めた話（最長一致と、手作りの表との差）
  - Playwright の E2E を Docker の Postgres と OpenAI のスタブで 190 件回している話
- 記事は README の「設計の要点」と `docs/architecture.md` からもリンクし、職務経歴書にも URL を書きます。
- 学习録の `/` のログイン前の案内に、「作った人」と GitHub・記事へのリンクを足します。

### J8. 技術面接の準備

- 学习録の説明を、1 分・5 分・15 分の 3 つの長さで話せるように書き起こし、録音して聞き直します。15 分版は J3 の図を見せながら話します。
- 聞かれそうな質問の一覧を作り、答えを書きます。例：「なぜ Go API を分けたか、Next.js だけで足りなかったのか」「認証を 3 通りにした代償は」「E2E が 190 件もあって遅くないか」「1 人で作ったものの、どこが設計で、どこが実装の都合か」「もう一度作るなら何を変えるか」。
- コーディング問題は、週に決めた数（「決めていないこと」）を解き、解いた日と内容を表に残します。学习録のコード（CSV のパース、最長一致、FSRS の計算）を題材に、口で説明しながら書き直す練習もします。
- システム設計の問題は、学习録の延長で 2 つ用意します：「会員が 1 万人になったら何を変えるか」「LINE の送信数の枠が尽きたらどうするか」。

### J9. 応募先の選び方と進め方

- 応募の条件（職種、勤務地、働き方、経験年数の要件、使いたい技術）を表にします。中身は「決めていないこと」です。
- 求人は、条件に合うものを週に決めた数だけ選び、学习録のどこが合うかを 1 行添えて応募します。
- 応募・書類の結果・面接の日・聞かれたこと・次に直すことを 1 つの表に残します。面接で答えられなかった質問は、J8 の一覧に足します。
- 月の初めに、書類の通過率と面接の通過率を見て、低いほうを直します。書類が通らないなら J6・J7 を、面接で落ちるなら J8 を直します。

### 「いつか」へ進む基準（＝節目 2）

- 1 社目に応募した。
- 応募を 5 社出した時点で、書類の通過が 1 社以上ある。0 なら、応募を止めて J1・J6 をやり直します。

## いつか（Later）：面接の結果を反映し、学习録を続ける（2027 年 4 月〜）

### J10. 面接で指摘されたことを学习録に反映する

面接で「ここはどうなっている」と聞かれて答えに詰まったところは、設計の弱点です。直せるものは直し、直さないものは `docs/architecture.md` の「いまの課題」に理由つきで書きます。直したこと自体が、次の面接の材料になります。

### J11. 内定後の学习録

内定が出たら、学习録をどうするかを決めます。候補は、使っている人のために維持だけ続ける、機能追加を再開する、公開を止めて記録だけ残す、の 3 つです。商用利用はしない前提は変えません。

### J12. ロードマップの残り

[ロードマップ](roadmap.md) の 5（間違いの傾向）と 12（練習の種類）は、応募が落ち着いてから再開します。面接で「次に作るなら」と聞かれたときの答えにもなります。

## 進め方の決まり

- 各項目を始めるときは、[ロードマップ](roadmap.md) の「今」にも番号を振って載せ、リリースしたらリリースノートに書きます。この文書の J 番号は変えません。
- 「次へ進む基準」を満たしたかどうかは、月の初めに 1 回だけ見ます。満たしていなくても、残りが 1 つなら 2 週間だけ延ばします。
- 応募を始めたら、学习録の変更は小さく保ちます。面接で見せるコードが、話した内容と違ってしまうのを避けるためです。

## 決めていないこと

- **LICENSE**：ソースを読んでもらうのが目的なので置きます。MIT にして使ってもらってよいか、読めるだけにして「All rights reserved」と書くか。
- **触れる経路（J2）**：デモアカウントか、動画か。デモアカウントは維持の手間（Cron で戻す、AI の制限）がかかり、動画は手間が少ないぶん触れません。両方にするなら、動画を先に作ります。
- **記事の置き場（J7）**：Zenn か Qiita か自分のサイトか。
- **応募の条件（J9）**：職種はフルスタックの Web エンジニアと決めました。勤務地、働き方、経験年数の要件、使いたい技術は、ここに表で書きます。
- **コーディング問題の量（J8）**：週に何問か。
- **学习録以外の経歴の扱い**：職務経歴書のどこに、どのくらいの分量で書くか。
